# archive-plex-anime 需求基线

## 1. 文档用途与事实来源

本文汇总用户对动画媒体归档 Skill 的长期目标、工作流、分支规则、执行边界和验收口径，帮助新会话快速理解项目。

精确执行时，已安装 Skill 的 `SKILL.md`、`references/`、当前配置和脚本是本机任务的直接事实来源；如果本文与当前 Skill 冲突，必须先报告差异，不得用本文覆盖正在使用的规则。

## 2. 项目定位

本项目用于在 Windows 上自动整理动画 TV 与 Movie 媒体，覆盖：

- 文件层级和标准命名；
- ASS 字幕识别、字体处理、子集化与 ZIP 累计归档；
- MKV 视频、音频、字幕、章节和附件的规范封装；
- TV/Movie 完整归档、洗版和原样入库；
- Movie 原盘音轨替换与 Plex `cdN` 堆叠电影；
- NAS 写入、Plex 维护表更新和最终清理；
- TMDB 为主、TVDB 为辅的作品名与季集辅助识别。

它以同一套归档规则核心支撑 CLI、独立 Skill 和 Bangumi Media Hub 适配层，而不是三套分别演进的工作流。仍应保持轻量：规则集中、步骤按需选择、检查最少、失败可恢复。

## 3. 项目版本边界

- 公开项目：`D:\project\archive-plex-anime`，必须保持可跨机配置、无凭据、无运行缓存和无本机私有资料。
- 本机安装版：`C:\Users\hm\.codex\skills\archive-plex-anime`，使用本机工具、路径和配置执行实际任务。
- 两者是刻意分离的发布版与安装版，未经差异核对、测试、打包和明确安装流程，不得直接互相覆盖。
- 本地审计、基础文档副本、测试包和构建 ZIP 可保留为 Git 忽略内容，不得未经审查推送公开仓库。

## 4. 媒体分支与任务模式

### 分支

- Anime 是 Plex 的 TV 库名，Anime 与 TV 指同一分支。
- 本机 `F:\pt&bt\anime\TV` 及其子目录属于 TV。
- 本机 `F:\pt&bt\anime\剧场版` 及其子目录属于 Movie。
- 路径必须规范化后按完整目录边界判断；不得把工作根本身作为作品任务目录。

### 模式

- `complete-archive`：用户说“完整归档”或“视频归档”时的默认完整流程；
- `replacement`：TV 或 Movie 洗版，按分支规则替换现有库内容；
- `archive-only`：用户明确要求不重新封装、原样入库；它是任务模式，不是完整流程中的一个步骤；
- `local-only`：只执行字幕、Movie 原盘音轨、remux、package 等指定本地能力及必要依赖，不进入最终 NAS/维护表阶段。

TV 和 Movie 使用同一套通用规则、工具、状态机和确认关卡，但各自保留季集、多分段、字幕、音轨和洗版逻辑。

### 预置与按需能力

- 四个现有模式同时作为版本化预置工作流保留；预置会按媒体实际情况跳过不需要的能力。
- 也可进入自定义模式，选择 `inspect`、`metadata`、`movie-audio`、`subtitle`、`remux`、`subtitle-package`、`video-delivery`、`subtitle-delivery`、`kdocs-tracker`、`cleanup`。
- 用户只选择公开能力；`prepare-fonts`、`subset`、`rename`、`review`、`finalize` 等内部步骤由统一解析器自动编排。
- 依赖自动补齐，例如字幕归档补齐字幕处理与打包，视频入库在需要时补齐 remux，remux 在实际存在字幕或 Movie 原盘音轨计划时补齐相应前序能力。
- `cleanup` 必须自动补齐 `video-delivery`；字幕 ZIP 或 KDocs 维护表不能单独解锁源目录清理。
- 自定义选择不含任何最终输出能力时按 `local-only` 规划，避免为了本地字幕/remux 无意义地检查 NAS 或维护表。
- 自定义模式未选择 `metadata` 时不得读取元数据凭据、构造客户端或访问 TMDB/TVDB；本地字幕、remux 和打包保持离线。此时若选择任何最终输出能力，必须通过 `decisions.title` 提供已确认标题。
- 预置模式与自定义模式互斥；`archive-only` 不接受处理型能力，TV 不接受 `movie-audio`，只有 `inspect/metadata` 的自定义空执行请求明确拒绝。
- CLI、Skill、Hub 使用同一能力目录。CLI 与 Skill 保留 KDocs；Hub 的能力目录、配置、工具检查、任务计划和执行结果均不包含 KDocs。
- 状态必须记录选择模式、预置及版本、入口、请求/解析/自动补齐/不可用能力、内部步骤和实际最终输出；重新初始化不同选择时旧计划、完成步骤和两次确认全部失效。

## 5. 统一工作流

```text
init
→ inspect
→ 用户前置确认
→ [movie-audio]
→ [subtitle]
→ [remux]
→ [package]
→ review
→ 用户确认本地产物及最终动作
→ finalize
→ cleanup
```

方括号步骤由预置或自定义能力、分支和媒体实际情况选择，不要求每次全部执行。计划只列所选工作流步骤，不逐文件展开产物。

正常完整任务只允许两次暂停：

1. 前检汇总后的前置确认；
2. 本地产物验收完成后，对产物和最终写入、维护表、清理动作的合并确认。

确认后如果输入、环境或正式目标发生变化，应返回失败并要求重跑受影响阶段，不临时增加第三个确认关卡。

## 6. 工作目录、状态与产物

- 用户给出的媒体目录同时是源目录和工作目录，不创建独立 `_work` 目录。
- ASS、最终 MKV 和 ZIP 直接输出在原目录，便于用户检查。
- 标准名称冲突时采用 Windows 编号形式：`文件 (1).ext`、`文件 (2).ext`，首次冲突从 `(1)` 开始。
- 重跑成功后只保留源文件和当前有效最终产物；失败的 remux 缓存、中间文件和旧轮次产物应按签名安全清理。
- 只允许以下隐藏工作内容：

```text
.archive-state.json
.archive-temp
.archive-logs
```

- 状态应支持按组件签名增量复检；局部输入变化只失效受影响组件和后续阶段，不重复全部前检。
- 所有路径、JSON、日志和命令参数使用 UTF-8；PowerShell 通过字节流或参数数组调用，禁止易破坏中文、`&` 和引号的拼接执行。

## 7. 前检范围与性能原则

前检只做完成当前任务所需的快速检查：

- 当前选中能力所需的工具和配置；
- 工作目录中的视频、MKA、ASS、字体和必要原盘源；
- 视频只读取封装轨道信息，不做整文件内容扫描；
- 字幕读取所需字体，并通过现有字体索引判断是否齐全；
- 目标库位、维护表和元数据只读取生成确定性计划所需的信息。

性能要求：

- 普通任务不检查 FFmpeg 等未选中能力的工具；
- MKV 封装串行，多个字幕组可以并行；
- 最终视频、字幕 ZIP 和维护表写入可并行；
- 普通视频只检查可读性、轨道和文件大小，不计算整文件哈希；
- NAS 写入前后使用快速大小比较；
- 前检缓存有效时按改动复检，不重复音频、字体或元数据的昂贵分析；
- 检查和计划不得比执行规则本身更臃肿。

## 8. TV 分支

### 层级与命名

```text
工作目录/Sx/作品名.SxxExx.mkv
工作目录/Sx/字幕组/作品名.SxxExx.ass
NAS Anime/作品名/Sx/作品名.SxxExx.mkv
ZIP Sx/字幕组/作品名.SxxExx.ass
```

- S1 及以上按源文件明确集数处理，每季从 `E01` 开始连续编号；无法解析时不得用文件名排序盲猜。
- S0 视频和各字幕组可按 NFKC、不区分大小写的数字自然顺序映射。
- S0 某集合使用任何显式映射时，该集合必须完整映射；数量不一致或用户未给定可靠规则时停止确认。
- 压制组全任务一致时使用 `release_group`；不同季用完整的 `release_group_by_season`。

### 音轨与章节

- 同名 MKV/MKA 自动配对，配对键必须包含相对父目录，避免跨季误配。
- 明确标为 Commentary、评论或解说的音轨可删除；其余歧义音轨由用户在前置确认选择。
- 只有一条 2.0ch 正片音轨时轨道名称留空。
- 多条正片音轨按用户确认顺序排列，唯一第一条为默认。
- 章节默认保留；最终新封装固定删除 PGS。

### 字幕排序

- 字幕按季独立排序，而不是全剧强制一套顺序。
- 用户可为每季显式给出完整、唯一的字幕组顺序。
- 未显式给出时，后一季优先沿用前一季已经出现且仍存在的字幕组及其相对顺序，再考虑更早出现和跨季覆盖。
- 同季排序依据仍相同时在第一次确认中由用户决定。
- 每集只对实际存在的字幕排序，该集第一条字幕是唯一默认轨。
- 已以 `JASC`、`JATC`、`SC`、`TC` 开头的目录标签为权威，不能重复添加语言前缀。

### TV 洗版

- `replacement` 或完整归档发现唯一同作品 WebRip 时，可执行 WebRip → BDRip 原位替换。
- 支持作品级 `（WebRip）` 和季级 `（S2 WebRip）` 等标记。
- 洗版后去除对应 WebRip 标记、更新维护表颜色和状态，并只删除同季同集旧媒体。
- 普通合法括号标题不得被误删。

## 9. Movie 分支

### 层级与堆叠电影

```text
工作目录/电影名[.cdN].mkv
工作目录/电影名[.cdN].[语言].字幕组.ass
NAS Movie/电影名/电影名[.cdN].mkv
ZIP 根目录平铺字幕
```

- 默认不增加年份、Edition 或额外子目录。
- 一个作品可以是单文件，也可以由 `cd1`、`cd2`、`cd3` 等 Plex 堆叠文件组成。
- 视频、字幕、原盘音轨和最终目标必须按相同 `cdN` 一一对应；不得拼接时长或删除堆叠标记。
- 作品名目录与 MKV 采用“电影名文件夹/电影名.mkv”结构。

### Movie 音轨与字幕

- 普通非 FLAC 正片音轨默认保留，按声道数从多到少排列，第一条默认。
- 音轨名称只写声道，如 `2.0ch`、`5.1ch`。
- 除非明确标注评论/解说/无障碍/伴奏或用户明确要求，否则不自动剔除音轨。
- FLAC 等特殊轨由前置决定精确选择。
- 章节默认保留；最终新封装固定删除 PGS。
- Movie 外挂 ASS 平铺，`cdN` 字幕只进入相同分段。
- 字幕组顺序由用户确认，组内语言顺序为 `JASC → JATC → SC → TC`。
- 多语言轨命名为 `JASC 字幕组` 等；每分段只有排序第一组中最前语言轨为默认。

### Movie 原盘音轨洗版

- 用户提供并已核实的 BDMV `STREAM` M2TS 或原盘提取 MKV 是原盘音频源。
- 使用压制版视频轨，只从原盘源复制音频；不使用原盘视频、字幕、附件或 PGS。
- 单文件或每个 `cdN` 分段独立配对，不允许交叉取轨。
- 以压制版 FLAC 为参考，结合声道数、布局、语言、时长、顺序和 3–5 个 PCM 采样点确定唯一原盘音轨与固定偏移。
- 无唯一完整匹配、非固定偏移或分段冲突时停在前检。
- 不转码、不变速、不拉伸、不静默裁切。
- 原盘中的正常音轨包括 FLAC 默认可保留；只有明确特殊轨或用户决定才删除。
- 中间封装只属于执行缓存，最终只保留规范 Movie 产物。

## 10. 字幕、字体与附件

### 无外挂 ASS

- 内封 ASS 与所需字体附件齐全且元数据规范：可跳过字幕处理和打包；
- 字幕与附件齐全但轨道命名、顺序、语言或默认状态不规范：只 remux 修正；
- 字幕或附件缺失：提取后进入子集化与打包；
- 完全无 ASS：停止并告知用户。

Movie 可在保留规范内封 ASS 和字体附件的同时增加外挂 ASS，两类字幕统一排序。

### 字体处理

- 前检只读取 ASS 所需字体，并依次查：工作目录字体 → assfonts 全局数据库 → 完整备用字体库的 `fc-subs.db`。
- assfonts 数据库本身代表主力字体库的可用映射，不重复遍历主力字体库。
- 字体缺失时在第一次确认中告知用户；用户补齐后可增量复检。
- 正常子集化直接调用 assfonts，以成功生成目标 ASS 作为成功标准。
- 只有 assfonts 失败后才针对日志明确指出的字体进行恢复。
- 候选同层优先 TTF，再按稳定路径排序并去重；只有命中 OTF/CFF 且确有需要时调用 otf2ttf。
- 每个任务最多重建一次经过验证的 assfonts 全局映射。
- TV 使用外挂 ASS 时不得继承无关源附件；最终附件只包含实际字幕需要的字体。

## 11. 封装与轨道契约

- 使用 MKVToolNix/mkvmerge 自动执行，不依赖 GUI 自动化。
- 每个输出完整声明视频、音频、字幕、章节和附件预期。
- 所有轨道必须显式设置名称、语言、默认、强制；音轨还应声明声道。
- 多来源 MKV/MKA 必须使用显式轨道顺序。
- 每个文件只能有一条默认音轨和一条默认字幕轨（没有字幕的合法分支除外）。
- 多视频轨在第一次确认中用精确 `video_keep` 选择唯一轨道。
- 新封装一律删除 PGS；不提供 PGS 保留分支。
- `archive-only` 必须验证源文件已经满足 TV/Movie 规范；含 PGS 或缺少完整 ASS/字体时停止，不自动切换任务模式。

## 12. 字幕 ZIP 累计归档

- TV ZIP 保留季/字幕组层级；Movie ZIP 根目录平铺。
- ASS 在 ZIP 前按最终规范名称重命名。
- 字幕 ZIP 是累计归档，不得用本次少量字幕直接覆盖历史 ZIP。
- 目标 ZIP 已存在时，本地产物先合并旧 ZIP 与本次字幕：保留旧独有条目，以本次条目替换规范化同路径冲突。
- review 阶段由用户检查完整合并 ZIP。
- 最终写入前后通过 ZIP 中央目录签名防止并发变化，不增加新的确认关卡。

## 13. 元数据辅助

- `inspect` 默认使用 TMDB，TVDB 只辅助核对或按用户要求提供季序。
- API 是辅助组件，不是第二套工作流；只生成标题、ID、季集摘要和映射建议。
- 自动搜索只提取作品名称，排除发布组、分辨率、编码、音轨、来源、版本、MKA、字幕、原盘和附加内容等噪声。
- 候选不唯一时在联网前要求用户给出查询词；不以文件数量等于 API 集数进行盲配。
- 用户明确标题、查询词、ID、季集映射和媒体分支始终优先。
- 用户前置确认后固化为普通决定，后续步骤不再联网。
- 四个预置工作流继续默认选择 `metadata`；自定义模式只有显式选择该能力时才执行元数据前检，未选择时记录稳定的 `OFF / CAPABILITY_NOT_SELECTED` 状态。
- TMDB/TVDB 默认可使用配置代理；凭据只从环境变量读取，不能写入状态、日志或仓库。
- API 不可用时按 `auto`、`required`、`off` 模式分别降级、停止或跳过。

## 14. NAS、维护表与清理

- TV 的 NAS 库位和维护表列一一对应 Anime1/2/3；Movie 使用对应 Movie1/2/3 单列。
- Movie 存储映射与 TV 相同，只把路径中的 Anime 替换为 Movie。
- 新归档在目标不存在时创建；洗版按已确认目标直接覆盖正式 MKV。
- 覆盖优先尝试同文件系统原子替换；不支持时采用直接替换备用方案，并在复制前后快速比较文件大小。
- 最终确认后，视频传输、字幕 ZIP 传输和维护表更新可以并行。
- 维护表按实际目标列写入；必须设置对应状态、颜色、对齐并确保新写入文字为加粗。
- 无法证明周边既有格式完全保留时仍可修改，但任务完成时必须告知用户。
- 清理永远最后执行。任何清理任务都必须先证明至少一个视频已在当前批次安全写入任务目录外的正式媒体目标；同时还要验证本次实际选择的字幕 ZIP 和维护表结果。字幕 ZIP 或 KDocs 成功不能替代视频入库证明。
- 删除任务目录、覆盖正式媒体和更新维护表都必须出现在最终确认摘要中。

## 15. 决策和安全契约

- 所有用户决定使用工作目录相对路径和稳定轨道键，禁止全任务模糊白名单。
- `video_keep`、`audio_keep`、`episode_map` 等决定必须精确作用于对应文件。
- 字幕组排序必须完整、唯一覆盖实际字幕组。
- 显式映射格式错误、季号错误、非正数集号或重复目标不能回退自动排序。
- 计划必须拒绝重复 MKV 输出、ZIP 条目和 NAS 最终目标。
- 前置确认前缺少可由用户决定的信息返回 `NEEDS_USER`。
- 前置确认后输入、环境或目标变化返回 `FAILED`。
- 删除前再次确认全部必要正式目标存在且大小一致。

## 16. 跨机安装要求

项目采用单配置、单助手、按任务检查，不引入 Profile 系统、自动安装器或复杂路径探测。

跨机使用时只向用户列出所需环境，由用户自行安装并填写配置：

- Python 3 与 fontTools；
- MediaInfo CLI、MKVToolNix、assfonts、otf2ttf；
- Movie 原盘音轨洗版所需 FFmpeg/FFprobe；
- CLI/独立 Skill 选择维护表能力时所需 KDocs CLI；Hub 不配置或检查 KDocs；
- TMDB 凭据和可选 TVDB 凭据、代理；
- 工作根、字体库、字体数据库、字幕归档根、NAS 映射和维护表库位。

工具路径可以不同，但字段语义、工作流和规则不变。只检查当前任务实际需要的能力。

## 17. 统一工具清单与 CLI

- `toolchain/manifest.json` 是工具名称、用途、入口范围、主页、下载页、固定制品、SHA-256 和能力 ID 的唯一人工维护事实来源；Schema 位于同目录，清单无效时必须明确失败。
- CLI、独立 Skill 和 Hub 使用同一清单的入口投影。Hub 投影只包含 MediaInfo CLI、MKVToolNix、FFmpeg/FFprobe 和 assfonts，不包含 KDocs 或 otf2ttf；CLI/Skill 继续保留可选 KDocs 和当前外部 otf2ttf 能力。
- 第一阶段提供 `tools list/check/use-path/export`：查看公开来源、执行最低能力检查、验证并保存已有绝对路径、生成确定性 Hub/Skill 投影。
- `use-path` 必须先完成全部最低能力检查，再原子修改单一配置；失败或回读异常时保留原配置，目录型工具同时写入现有工作流使用的具体可执行路径。
- 清单和投影不得包含凭据、本机路径、代理、安装状态、媒体规则或任务状态；Hub 入口不得解析、检查、显示或导出 KDocs。
- 工具缺失时 `list` 仍返回项目主页和官方下载页；`check` 只运行明确选中的工具，状态限定为 `ready`、`missing`、`not_configured`、`unsupported_platform`、`capability_failed`、`needs_recheck`。
- 第一阶段不提供 `tools install/update/rollback`，不下载制品，不从网页抓取“最新版”，也不接受任意下载 URL。固定制品字段只为后续受管安装预留。
- 媒体工作流仍按本次选择的能力检查工具，未选择的工具不得因为清单存在而被检查；工具管理模块不读取媒体目录或修改 TV/Movie 规则。

## 18. 轻量化与代码结构要求

- 静态不变量集中在规则/契约模块，不能在多个步骤重复解释。
- TV 与 Movie 共享通用步骤实现，各分支计划器只处理自身差异。
- 每个工作流步骤都应有可直接调用的代码模板或 CLI 入口。
- 不保留 legacy 目录、旧状态迁移、备用入口或第二套工作流。
- 测试按当前行为、关键安全边界和历史回归价值保留；删除只验证旧版实现细节的测试。
- 公开的纯 Python 能力、Hub 投影、清理安全和元数据门控回归测试必须纳入 Git；真实媒体样本和本机私有夹具可继续排除。
- 开发检查使用 `requirements-dev.txt` 固定的 Ruff 版本；Windows 与 Linux CI 统一运行公开测试、`ruff check --no-cache scripts` 和 `git diff --check`。
- 构建和测试不得产生 `.pyc`、`__pycache__` 或把运行缓存打入 ZIP。
- 每次发布 ZIP 应从安装/发布源构建，排除配置、凭据、缓存、测试数据和本机私有文档，并校验文件一致性。

## 19. 验收口径

- 前检能用最少读取生成无歧义计划，且只在两处请求确认；
- TV/Movie 按各自层级、命名、字幕和音轨规则生成本地产物；
- 用户能直接在原目录检查最终 ASS、MKV 和累计 ZIP；
- remux 后轨道、章节、附件、默认状态和压制组完整正确，PGS 已删除；
- 局部补文件或修改决定后只重跑受影响检查；
- NAS 视频、ZIP 和维护表在最终确认后完成写入，大小与目标一致；
- 维护表新写入文字确实加粗；
- 最终清理不删除未安全归档的源目录，也不留下失败缓存和多轮无效产物；
- 普通任务不做整文件哈希、不深检无关工具，速度与本机已验证任务保持同等级；
- 公开仓库保持纯净、可配置且不包含本机敏感信息。
- 同一清单能够稳定生成 CLI、Skill 和不含 KDocs 的 Hub 投影；路径检查失败不会改变原配置，第一阶段不会下载或安装工具。

## 20. 新会话执行原则

如果新会话只是修改项目源码，应以本仓库当前规则、测试和公开配置为范围。如果执行实际媒体任务，必须切换到本机已安装 Skill，完整阅读其 `SKILL.md` 和所需引用文件，并严格执行两次确认工作流。
